# TRPG_Agent Root Prompt

## 0. LLM 读取本仓库时的第一指令

当你读取本仓库时，不要把它理解为一个普通 TRPG 模组仓库，也不要把它理解为单纯的设定资料库、规则书、Wiki 镜像或聊天 Prompt 集合。

你应当把本仓库理解为：

**一个以 ACGN / 游戏作品资料为输入，以 Skill 系统与 GraphRAG 为中枢，将原作世界观、Wiki、角色、地点、道具、敌人、任务与叙事结构转化为可运行 TRPG 战役底座的 AI GM Agent 框架。**

当前仓库以《艾尔登法环 / Elden Ring》作为首个 world_base 实例，但项目目标并不局限于《艾尔登法环》。它的长期目标是支持任意 ACGN / 游戏 IP 被转译为可游玩的 TRPG 世界。

---

## 1. 项目核心愿景

TRPG_Agent 的核心远景是：

**构建一个能够读取作品资料、生成 TRPG 世界底座、驱动 AI GM 进行长期战役，并在运行过程中持续检索、裁定、记录、更新世界状态的通用 TRPG Agent 框架。**

它的最终形态不是“一个固定剧本”，而是一个开放式作品世界跑团引擎。

玩家输入一个作品世界，例如：

* 《艾尔登法环》
* 《鸣潮》
* 《东方Project》
* 《碧蓝航线》
* 任意具备世界观、角色、实体、地点、规则或 Wiki 资料的 ACGN / 游戏作品

系统应读取该作品的资料源，并将其转化为：

* 可执行规则系统
* 可构建角色系统
* 可检索内容实体系统
* 可持续推进叙事系统
* 可写回状态的长期战役数据

最终目标是让玩家能够在原作世界观边界内，进行比原电子游戏更自由的 TRPG 行动。

---

## 2. 第一性原则

读取、扩展或运行本仓库时，必须遵守以下优先级：

### 2.1 原作事实优先

原作中已经明确存在的事实、地点、NPC、道具、Boss、掉落、任务线、结局路线、术语，应优先遵守原作与 Wiki 资料。

不得随意伪造：

* 固定掉落
* 固定地点
* NPC 所在位置
* NPC 任务触发条件
* Boss 奖励
* 地图连通关系
* 原作专有术语含义

当资料不确定时，应标记为“需 Wiki 核验”，而不是直接补全为确定事实。

### 2.2 TRPG 适配其次

原作游戏不一定具备桌面规则。例如《艾尔登法环》原作没有显式掷骰系统、没有传统 TRPG 检定 DC、没有完整社交判定。

因此，本项目允许将原作机制转化为 TRPG adapter / homebrew logic。

但所有 TRPG 化内容必须明确标记为：

* adapter
* homebrew
* generated_from_skill
* generated_from_world_base
* non-canon rule conversion

不得把 TRPG 化规则伪称为原作硬规则。

### 2.3 GM 裁定最后兜底

当原作资料与 TRPG adapter 都不足以支撑结算时，AI GM 可以进行裁定。

但裁定必须遵守：

1. 不违背已知原作事实。
2. 不破坏当前战役状态。
3. 不跳过已有规则系统。
4. 不替玩家做关键决策。
5. 必须说明裁定依据。
6. 需要写回战役状态时，应标明写回目标。

## 3. 本仓库的核心抽象

本仓库采用四层结构组织 TRPG Agent 的认知与执行逻辑。

### 3.1 规则执行层

回答问题：

**现在该如何判定？**

负责处理：

* 基础判定
* 对抗
* 行动经济
* 攻击与防御
* 伤害与治疗
* 状态
* 资源消耗
* 休息与恢复
* 探索与旅行
* 社交互动
* 魔法、技能与特殊能力执行
* 规则优先级与例外

### 3.2 角色构建层

回答问题：

**角色为什么拥有某能力？**

负责处理：

* 基础属性
* 种族、血统或物种
* 职业
* 子职业、专精或流派
* 背景
* 等级成长
* 技能与熟练
* 专长、天赋与特性
* 装备构建
* 法术与能力列表
* 角色定位与战术角色
* 角色状态快照

### 3.3 内容实体层

回答问题：

**某个对象的规则属性是什么？**

负责处理：

* 能力实体
* 武器实体
* 护具与防御装备
* 道具与消耗品
* 法术实体
* 敌对单位与怪物
* NPC 实体
* 环境实体
* 陷阱与机关
* 疾病、毒素与诅咒
* 遭遇实体
* 奖励与掉落

### 3.4 叙事运行层

回答问题：

**当前故事发生了什么，以及规则如何作用于故事？**

负责处理：

* 世界观
* 地图与地点
* 场景
* NPC 与关系网络
* 派系
* 任务
* 线索与信息
* 冲突
* 遭遇节点
* 战役状态
* 时间推进
* GM 裁定与自制规则

---

## 4. GraphRAG 的职责

GraphRAG 不是普通资料索引。

在本项目中，GraphRAG 的职责是：

1. 将玩家输入、Wiki 条目、角色卡、实体对象、剧情状态或规则片段定位到对应层级。
2. 在层级内部继续定位到具体 system logic。
3. 建立不同系统之间的依赖关系。
4. 指明需要检索哪些文件。
5. 指明哪些结果需要写回状态。
6. 当术语不一致时，保留 source_term，并映射到 normalized_term。
7. 当无法直接命中时，给出候选系统，而不是随意生成答案。

GraphRAG 的核心路由方向是：

玩家输入
→ 判断属于哪一层
→ 判断属于哪个系统
→ 检索相关 logic
→ 检索相关实体 / 场景 / 状态
→ 执行规则或叙事推进
→ 写回角色状态与战役状态

---

## 5. Skill 的职责

Skills 不是运行时剧情文本。

Skills 是系统生成器。

每个 Skill 的职责是从作品资料、Wiki、规则文本、角色档案、战役记录或自制设定中，抽象出一个稳定的 TRPG system logic。

因此，读取 Skills 时，应理解为：

* Skills 定义“该类系统应该如何被抽象”
* RAG 文件定义“输入如何路由到该系统”
* RAG_logic 定义“某个作品实例化后的 world_base”
* Runtime 才负责“在具体游戏中执行”

不得把 Skill 文件直接当成最终游戏内容。

## 6. 当前仓库的阶段定位

当前仓库已经具备：

* 四层 Skill 架构
* 48 个 Skill 文件
* 四层 GraphRAG 路由结构
* Elden Ring world_base logic
* YAML / JSON 双格式系统输出
* 术语映射表
* 节点与边表
* 输入资料源记录
* 自检与限制说明

因此，当前仓库可以作为：

**TRPG Agent 的 world_base / RAG brain / 规则与世界资料底座。**

但它还不应被误判为已经完成的独立运行程序。

若要成为完整可运行 TRPG Agent，还需要补充：

* runtime / orchestrator
* LLM 调用层
* RAG 检索器
* 持久化状态文件或数据库
* 掷骰与规则计算器
* Wiki 核验模块
* session log
* 角色卡系统
* 测试用例
* CLI / Web / Bot 交互入口

## 7. Agent 运行时的理想闭环

一个完整 TRPG_Agent 在运行时应遵循以下闭环：

1. 接收玩家输入。
2. 判断输入是行动、查询、对话、战斗、探索、休息、交易、升级、任务推进，还是 GM 裁定请求。
3. 调用 Master GraphRAG Router。
4. 定位到四层之一或多个层级。
5. 检索相关 system logic。
6. 检索相关角色、实体、地点、任务、状态。
7. 若涉及原作固定资料，调用 Wiki 核验。
8. 若涉及不确定行动，执行 TRPG 判定。
9. 若涉及战斗，执行行动经济、命中、防御、伤害、状态、资源消耗。
10. 若涉及叙事，推进场景、NPC 关系、任务阶段或时间。
11. 输出 GM 叙事与规则结算。
12. 写回角色状态、战役状态、背包、任务 flags、地图 flags、NPC flags。
13. 保存 session log。
14. 等待下一次玩家输入。

该闭环的核心原则是：

**每一次输出都应尽可能来自“原作事实 + TRPG logic + 当前状态”，而不是孤立生成。**

---

## 8. 对玩家自由度的设计目标

本项目不应只复现原电子游戏流程。

TRPG_Agent 应允许玩家做出原作游戏中无法直接表达，但在 TRPG 中合理的行动，例如：

* 潜行绕过敌人
* 与 NPC 深度交涉
* 侦查敌方营地
* 制造埋伏
* 利用地形解决战斗
* 招募或说服中立单位
* 改变任务介入顺序
* 提前调查隐藏信息
* 使用非常规手段获取道具
* 通过团队协作改变遭遇结果
* 在原作路线之外做出合理选择

但这些自由行动必须经过规则系统与世界状态约束，不得无成本实现。

---

## 9. 对《艾尔登法环》实例的特殊约束

当当前 world_base 指向《艾尔登法环》时，必须遵守：

1. 赐福可以作为安全点、恢复点、地图节点、休息入口与状态保存入口。
2. 卢恩同时具有成长资源、货币、死亡风险资源三重功能。
3. 状态异常应按积累值、阈值、触发效果、解除手段建模。
4. 固定掉落、固定地点、NPC 任务线、Boss 奖励必须 Wiki 核验。
5. 原作没有显式掷骰，因此所有 d100、DC、检定、社交判定都属于 TRPG adapter。
6. 世界观应保留破碎战争、黄金律法、半神、大卢恩、赐福、褪色者、双指、癫火等原作核心概念。
7. TRPG 运行中允许玩家做出原作中不存在的自由行动，但不得随意推翻原作基础事实。

## 10. LLM 读取仓库时的推荐顺序

任何 LLM 读取本仓库时，应优先按以下顺序理解项目：

1. 读取根 README。
2. 读取 `RAG_logic/README.md`。
3. 读取 `RAG_logic/skill_execution_manifest.json`。
4. 读取 `RAG_logic/graph/00_master_router_elden_ring_instance.json`。
5. 读取 `RAG_logic/graph/nodes.json` 与 `RAG_logic/graph/edges.json`。
6. 读取 `RAG_logic/input_sources.json`。
7. 读取 `RAG_logic/audit/self_check.md`。
8. 按需求读取 `RAG_logic/systems/<layer>/<system>.yaml` 或 `.json`。
9. 如需理解生成规则，再读取 `Skills/01-04`。
10. 如需理解抽象路由，再读取 `RAG/00_MasterLayerGraphRAG_Router.js` 与四层 GraphRAG JS 文件。

不要一开始就陷入单个 JSON 文件细节。应先理解项目愿景、层级结构、路由逻辑与运行边界。

---

## 11. 禁止误解

读取本仓库时，禁止做出以下误判：

1. 不要把本仓库理解为完整 Wiki 镜像。
2. 不要把本仓库理解为固定剧本。
3. 不要把本仓库理解为单一《艾尔登法环》模组。
4. 不要把 Skill 文件理解为最终战役内容。
5. 不要把 TRPG adapter 理解为原作硬规则。
6. 不要在没有 Wiki 核验的情况下断言固定掉落、NPC 任务、Boss 奖励。
7. 不要跳过 GraphRAG 路由直接生成结论。
8. 不要忽视状态写回。
9. 不要将一次性问答当成长期战役。
10. 不要让 AI GM 的自由发挥覆盖原作事实。

---

## 12. 输出标准

当 LLM 基于本仓库回答问题、运行战役或扩展系统时，输出应尽量满足：

* 明确调用了哪个层级
* 明确调用了哪个 system logic
* 保留原作术语
* 给出 normalized_term
* 区分原作事实与 TRPG adapter
* 涉及固定资料时提示 Wiki 核验
* 涉及规则时给出结算流程
* 涉及状态时说明写回目标
* 涉及不确定信息时标记置信度或待核验
* 不输出隐藏推理链，只输出必要的决策摘要、规则依据与结果

---

## 13. 项目一句话定义

**TRPG_Agent 是一个以原作资料为事实边界，以 TRPG 规则为交互骨架，以 GraphRAG 为调度中枢，以 AI GM 为表现层的开放式作品世界跑团引擎。**

它的目标不是替代原作，也不是复述原作，而是让原作世界成为可以被长期游玩、持续记录、规则驱动、自由行动的 TRPG 战役空间。
